# Review of HTTP and its TCP integration

Commit: `0be8fc1` (0.1.0); HTTP implementation: `75fab71`.
Scope: the latest HTTP integration (`92a6d7b..0be8fc1`) and the TCP paths it uses.
It does not exhaustively cover every phase since the previous audit.

Status: review complete. The tree was clean at the start. No production code
is modified. Working branch: `fix/audit-http-0be8fc1`, with no commit or merge.

## Validation

- `build/audit/0be8fc1/check.log`: `cargo xtask check`, passed.
- `build/audit/0be8fc1/tests.log`: `cargo xtask test --all`, passed:
  **130 unit tests and 54 QEMU scenarios**, including HTTP, TCP and shell.
- Additional tests: **9 tests, 1 passing and 8 failing**, in both debug

The tests load the original crates and `sdk/rust/src/http.rs`, replacing
only `NetClient` with a deterministic in-memory transport that honours the
1472-byte maximum per read. They make no AriCodeOS syscalls or network connections.
They check the parser and the SDK logic; they are not presented as additional
QEMU reproductions. The DNS test calls the original protocol without simulating it.

## 1. [P1] A chunk size can make the client panic

Code: [libs/http/src/lib.rs](../../libs/http/src/lib.rs), lines 150–157.

`size` is parsed as `usize`, but `data_start + size` and `data_end + 2`
do not use checked arithmetic. A representable length that overflows the sum
panics in debug. In release the sum wraps and reaches a copy whose range does
not exist in the input: it also panics.

Reproduction: `chunk_size_arithmetic_does_not_panic`. The input contains only
a size line; rejection or an incomplete-data indication is expected.
Debug fails with an overflow at line 151; release with an out-of-bounds range
at line 157. In the current programs the panic handler terminates the process
(`user/testprogs/src/lib.rs:118–121`), so no `HttpError` is returned to the
caller. No memory corruption or kernel crash has been observed or is claimed.

Fix: check the sums and all bounds before copying; distinguish invalid
input from incomplete input. Keep regressions in both profiles.

## 2. [P2] A 4 KiB chunk is rejected even though the body fits the destination

Code: [sdk/rust/src/http.rs](../../sdk/rust/src/http.rs), lines 113–126;
[libs/http/src/lib.rs](../../libs/http/src/lib.rs), lines 150–153.

The SDK uses a fixed 4096-byte scratch buffer and the decoder requires the
complete chunk, including its delimiters, before consuming it. A single
4096-byte chunk needs more scratch space, even if the destination has
4096 bytes or more. The result depends on the chunk size chosen by the
server, not only on the body size.

Reproduction: `chunk_4096_fits_caller_buffer` returns `Err(TooBig)` instead of
`Ok(Fetched { status: 200, body_len: 4096 })`.

Fix: keep decoding state across reads and consume the content in pieces.
Enlarging the scratch buffer does not fix the general API, whose destination
is supplied by the caller. Cover chunks larger than the scratch buffer and
fragmentation at the boundaries of the size line and of the content.

## 3. [P2] A TCP reset turns an incomplete download into success

Code: [sdk/rust/src/http.rs](../../sdk/rust/src/http.rs), line 107.

In `UntilClose`, `Status::Reset` ends the loop just like a clean EOF and the
SDK returns `Ok` with the bytes received so far. The explicit transport error
signal is lost and the caller may treat partial content as a complete
download.

Reproduction: `reset_is_not_successful_completion` delivers seven body bytes
followed by a reset; it gets `Ok(Fetched { status: 200, body_len: 7 })`.

Fix: propagate the reset as `HttpError::Io` or an incomplete-response
error. A close with an error does not complete a close-delimited response,
per [RFC 9112, section 8](https://www.rfc-editor.org/rfc/rfc9112.html#section-8).

## 4. [P2] An interim response is returned as the final result

Code: [sdk/rust/src/http.rs](../../sdk/rust/src/http.rs), lines 65–67;
[libs/http/src/lib.rs](../../libs/http/src/lib.rs), lines 90–93.

The SDK leaves the header loop on receiving the first response, without
checking whether the status is interim. The parser assigns `UntilClose` to a
103 without length headers. A final response that follows ends up copied,
headers included, as the supposed body of the 103 response.

Reproduction: `informational_response_is_not_final` delivers a 103 followed
by a 200 with five bytes. It gets status 103 and a 43-byte body instead of
status 200 and five bytes.

Fix: consume informational responses and continue until the final one,
keeping the bytes already received. [RFC 9110, section 15.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.2)
requires being able to process 1xx responses preceding the final one. Define
the rejection of unsupported protocol switches separately.

## 5. [P2] Header order changes how the body is interpreted

Code: [libs/http/src/lib.rs](../../libs/http/src/lib.rs), lines 99–106.

Each header overwrites `body`: if `Content-Length` appears after
`Transfer-Encoding: chunked`, the result is no longer `Chunked`. The SDK may
return encoding bytes as if they were body, truncate them or wait for
the wrong amount. It does not reject the ambiguous combination.

Reproduction: `transfer_encoding_not_overridden_by_content_length_order` receives
both headers in that order and gets `Length(50)`.

Fix: collect and validate the headers before resolving the framing;
reject the combination or give Transfer-Encoding precedence, regardless
of order. This precedence is defined in [RFC 9112, section 6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3).

## 6. [P2] A close-delimited body cannot exactly fill the destination

Code: [sdk/rust/src/http.rs](../../sdk/rust/src/http.rs), lines 100–105.

On reaching `out.len()`, `TooBig` is returned before checking whether the next
transport result is EOF. A body that fits exactly is therefore rejected.
An empty response with an empty destination also fails.

Reproduction: `close_delimited_body_exactly_fits` delivers five body bytes
with a clean close and a five-byte destination; it gets `Err(TooBig)`.

Fix: when the destination is full, probe with a one-byte auxiliary buffer
to distinguish EOF, excess content and error. Cover zero size,
exact capacity and capacity plus one byte.

## 7. [P2] The integration accepts names that DNS silently truncates

New integration code: [sdk/rust/src/http.rs](../../sdk/rust/src/http.rs),
lines 33–38. Pre-existing dependency: [sdk/proto/src/lib.rs](../../sdk/proto/src/lib.rs),
lines 318 and 397–402; [sdk/rust/src/net.rs](../../sdk/rust/src/net.rs), `resolve`.

HTTP accepts the full name, but `Request::with_name` truncates it to
`MAX_NAME = 40` when sending it to netd, without reporting an error. A longer
valid name is looked up as a different name and may fail to resolve or return
a different address. This limit dates from phase 22; the HTTP integration
inherits it without validating it.

Reproduction: `dns_request_preserves_hostname` uses a 43-byte name with
valid labels. The protocol keeps only 40 and turns the `.test` suffix
into `.t`.

Fix: carry the full name or explicitly reject the excess before resolving.
Do not truncate destination identifiers. The nominal HTTP test uses a
literal IP, so it does not exercise this path.

There is a second truncation in `write_host` (`sdk/rust/src/http.rs:149`), at 74
bytes. The `host_header_preserves_long_hostname` test, with simulated resolution,
confirms it; it does not establish that real DNS resolves that full name with the
current protocol. If DNS is extended, also fix the `Host` construction.

## Resolution

Fixed on the `fix/audit-http-0be8fc1` branch (2026-09-27). The HTTP logic
moved to `aricode-http` behind a `Transport` trait, so the audit
regressions now live as host tests of the crate
(`libs/http/src/lib.rs`) with a simulated transport that honours the
1472-byte maximum per read; the SDK (`sdk/rust/src/http.rs`) only adapts
`NetClient`. `reproduce.py` was updated to the fixed API and exits with
code 0 in both profiles (9 tests passing).

| # | Finding | Fix | Regression |
|---|---------|-----|------------|
| 1 | Panic from chunk size | Stateful `ChunkDecoder`; the size is validated (hex up to 15 digits, 256-byte line) and never added unchecked; invalid input → `ChunkError`, incomplete → no progress | `chunk_decoder_rejects_garbage_without_panicking` |
| 2 | 4 KiB chunk rejected | Incremental decoder: copies the chunk data in pieces; the reader's scratch buffer is 1 KiB and does not limit the chunk size | `chunk_larger_than_scratch_fits_caller_buffer`, `chunk_decoder_streams_across_boundaries` |
| 3 | TCP reset taken as success | Every transport error is propagated as `Error::Transport`; only `Ok(0)` completes a close-delimited body | `reset_is_not_successful_completion` |
| 4 | 1xx returned as final | The reader consumes informational responses and continues with the remaining bytes; 101 → `Unsupported` | `informational_responses_precede_the_final_one` |
| 5 | Header order changes framing | All headers are collected: `Transfer-Encoding: chunked` takes precedence; any other encoding, repeated `Content-Length` with differing values, or non-numeric → invalid response | `response_headers_and_framing_precedence` |
| 6 | Close-delimited body cannot fill destination | With the destination full, a one-byte probe is made: EOF → success, data → `TooBig`, error → `Transport` | `close_delimited_body_exactly_fits`, `reset_is_not_successful_completion` |
| 7 | DNS truncates names to 40 bytes | The name travels whole in the client's DMA buffer (`len`, up to 253) and the message drops the `name` field; `Url::parse` rejects hosts longer than 253 bytes and the `Host` header is built without truncation; `fs::Request::with_name` returns `None` instead of truncating (same defect in the file protocol) | `long_hostname_is_kept_whole_in_host_header`, `dns_request_preserves_hostname` (probes), `fs_request_and_reply_round_trip` |
| doc | README announces 0.0.7 | Status updated to 0.1.0 with the current services | — |

In addition, while reviewing netd's error paths it was found that some
requests with a buffer returned without closing the client's buffer handle
(handle leak on errors). The main loop now owns the handle
and only the pending request that will use it keeps it (`Stack::retained`).
