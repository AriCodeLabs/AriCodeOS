# bench3d material textures (2026-11-07)

## Content and provenance

`textures=v2` replaces the 256x256 checker with four original materials generated by
`desktop/bench3d/src/materials.rs`. The source and its generated artwork are Apache-2.0;
there are no third-party image assets. Integer hashes, periodic value noise, planks,
mortar, bevels, nails and rivets generate the top levels. The existing renderer builds
all mip levels down to 1x1 and samples them with its existing filters.

| Material | Size | Texel storage including mipmaps | Used by |
|---|---:|---:|---|
| Braced wooden crate, grain and nails | 128x128 | 87,380 bytes | nearest, linear, corridor, objects |
| Dressed stone, staggered blocks and mortar | 128x128 | 87,380 bytes | corridor, objects |
| Earth, moss patches and small stones | 128x128 | 87,380 bytes | terrain, everything |
| Worn steel, seams, rivets and rust | 64x64 | 21,844 bytes | objects, everything |
| **Total** | | **283,984 bytes** | |

The checker used 349,524 texel bytes. This replacement saves **65,540 bytes** in texels;
level descriptors and allocator headers are additional and included in the measured
heap totals below. No texture is generated or decoded during measured frames.

## Format comparison and decision

Three equivalent release packages were built and booted on the development host in
QEMU, each with the same four images, mipmaps, scene code, instrumentation and quota.
These are startup observations, not laptop performance results. The original package
at `53665df`, before instrumentation and allocation changes, was **746,424 bytes**.

| Representation | Complete signed package | Texture construction, including mipmaps | Startup through window creation | Heap free at startup |
|---|---:|---:|---:|---:|
| Procedural, selected | **759,240 bytes** | 5,808 us | 456,082 us | 328,192 bytes |
| RGB24 `include_bytes!` | 910,792 bytes | 1,707 us | 442,584 us | 328,192 bytes |
| QOI `include_bytes!`, `qoi =0.4.1` | 829,000 bytes | 2,930 us | 491,467 us | 328,192 bytes |

RGB24 embeds 159,744 bytes. The exact same images encode to 76,689 QOI bytes
(24,694 + 18,260 + 25,147 + 8,588). The QOI candidate uses
[`qoi` 0.4.1](https://docs.rs/qoi/0.4.1/qoi/), a pure Rust, MIT OR Apache-2.0 decoder,
with `default-features = false`; its host encoder additionally enables `alloc`.
The candidate decodes one image at a time into a fallibly reserved RGB24 buffer:
49,152 temporary bytes for a 128x128 image, released after its mip chain is built.
Procedural and raw loading write directly into the texture's top level and need no
such buffer. All candidates use the same resident texture storage. Embedded image
data increases the ELF/package footprint in addition to that heap storage.

Choose **procedural**: the package is 69,760 bytes smaller than QOI and 151,552 smaller
than RGB24, with no image decoder dependency or temporary decoded image. Its extra
4.1 ms of texture setup versus raw data in this QEMU observation is paid once; measured
frames only sample texels. Total startup also includes buffers, mesh construction,
the pre-rendered effects image and window creation, so its variation is not a decoder
benchmark. A host release probe averaged 750 us over 100 procedural constructions;
that host figure is likewise not a laptop or guest performance claim.

The comparison can be regenerated without changing production dependencies. Each
candidate has the same package/binary name, and xtask shares `build/external/bench3d-v1`
between them: clean the app artifacts when switching directories. Otherwise Cargo can
consider the earlier directory fresh while the public output binary belongs to the
last candidate built. The first final rerun caught precisely this with the reduced-heap
binary; its failed log is retained as `bench3d-textures-stale-artifact-gui.log`.

```sh
python3 -I desktop/bench3d/tools/texture-options.py ~/aricode-scratch/texture-options
for mode in procedural raw qoi; do
    cargo clean --manifest-path ~/aricode-scratch/texture-options/$mode/Cargo.toml \
        --target-dir build/external/bench3d-v1 --target x86_64-unknown-linux-gnu --release -p desktop-bench3d
    cargo xtask app-pack ~/aricode-scratch/texture-options/$mode --version 1
done
```

For each guest measurement, temporarily point the scenario's `install` entry at the
candidate directory, clean/rebuild that candidate, run
`cargo xtask test --only gui.bench3d`, and preserve its serial log before the next run.
Restore `install = ["desktop/bench3d"]` afterwards and clean/rebuild the production
package too. The script verifies that QOI decodes to the identical RGB24 source bytes. It builds only Rust;
no downloaded C implementation is compiled. QOI is confined to comparison directories
outside the repository and is not in the shipped app's dependency graph or lockfile.

## Memory and failure behaviour

The manifest remains **8 MiB**, and `libs/manifest::MAX_MEMORY_KIB` is unchanged.
The window consumes 1,876 KiB (page-rounded 800x600x4) and `MORE_HEAP` still requests
6,144 KiB: **8,020 of 8,192 KiB**, leaving **172 KiB of DMA quota**. This is distinct
from free space inside the heap. The heap includes the existing static 256 KiB arena,
for 6,553,600 managed bytes in total.

The selected package reported **328,192 heap bytes free at startup** and **290,256
bytes free after the 13 quick scenes**, including their font cache and results.
These are allocator snapshots, including headers/alignment, not a claimed minimum
at every instruction. `aricode_rt::heap_stats()` reads those existing allocator counters
under its lock without allocating. Later runs may differ slightly with HUD glyphs.
The final clean production rerun left 328,192 bytes at startup and **290,192 bytes
after all scenes**, with `startup_us=464227` and `texture_us=7898`. The same 759,240-byte
package passed all 13 scenes in 19.6 s of scenario time; all metric lines had `n=3`,
ordered percentiles and the v2 header. Its three final PNGs were inspected again.

All scene buffers, the four mip chains, five meshes and 4,096 timing samples are now
reserved fallibly at startup. Partial allocations unwind normally on failure. The
texture and grid constructors reject invalid/overflowing dimensions. Once the assets
and samples fit, startup also tests a contiguous **256 KiB runtime reserve**, then
releases it for the 96 KiB glyph cache, font hinting/scratch and small HUD/result strings.
Failure returns through `bench3d: no memory for its scenes` before opening a window.
The existing infallible render3d constructors remain available to existing callers.

The timing vector is reused between scenes and sorted in place after measurement,
removing a 16 KiB percentile clone. Effects use a 25-float stack kernel instead of a
per-frame heap allocation. The colour/depth/effects buffers retain their dimensions;
`App::back` and the full finished-frame copy in `App::show` are preserved.

An allocator-injection unit test fails every allocation in turn in texture and mesh
construction and checks that partially built assets release all allocations. A separate
scratch package reducing `MORE_HEAP` from 6,144 to 5,888 KiB tests the startup reserve
failure path in QEMU; the production budget is unchanged.

## Comparability and visual checks

Every run header now includes `renderer=cpu textures=v2`. The scene metric lines remain
`bench3d.<scene> us p50 p95 p99 max= n= fps= ...`, including the existing triangle,
pixel and temperature fields. The names and count of 13 scenes are unchanged.

Content changes affect the three texture scenes, terrain, objects, everything, and
both 2D effects (their source image comes from everything). Geometry, dense geometry,
the two standalone shading scenes and desktop retain their scene content. Treat v2
as a new benchmark dataset; the laptop's bench3d 2 results in ADR 0080 section 4c are
preserved and must not be treated as a speed regression or improvement for changed
content. No new laptop figures were collected for this change.

`gui.bench3d` captures texture-linear, objects and everything. Quick mode holds those
completed frames for 500 ms **outside** the measured intervals, so QMP captures the
intended scene. The normal five-second benchmark has no added pauses. Inspect with:

```sh
python3 -I ~/aricode-scratch/ppm2png.py build/scenarios/gui.bench3d/scene.ppm
python3 -I ~/aricode-scratch/ppm2png.py build/scenarios/gui.bench3d/objects.ppm
python3 -I ~/aricode-scratch/ppm2png.py build/scenarios/gui.bench3d/everything.ppm
```

All three PNGs were visually inspected: the crate's grain, braces and nails are visible;
objects alternate wood, stone and rusty steel; everything has a textured landscape
and metal objects. No cut models or unfinished frame regions were seen. The four source
material swatches were also inspected at 128x128 / 64x64.
