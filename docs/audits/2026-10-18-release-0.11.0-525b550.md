## 1. [P1] EHCI acknowledges a write without receiving a complete CSW

Code: [services/usb-ehci/src/main.rs](../../services/usb-ehci/src/main.rs),
`Ehci::scsi`, lines 2684–2696. Introduced with the EHCI driver in this range.

The CSW bulk read returns the number of bytes transferred, but `scsi`
checks only whether the call returned an error. It then reads all 13 bytes
of the persistent CSW buffer and passes that array to `check_csw`.

A short reply containing the four-byte signature and the current four-byte
tag replaces the first eight bytes. The residue and status remain from
the previous command. If those old bytes say zero residue and Passed,
`scsi` returns `Ok(0)`. `block_io_within` consequently reports a successful
write although the device supplied no status for that command. The same
length omission exists in the recovery CSW read in `transfer_failure`.

Reproduction: the probe runs the extracted `Ehci::scsi` with a completed
512-byte WRITE(10) data transfer and an eight-byte CSW, over a buffer whose
previous residue and status are zero:

```text
EHCI: 8-byte CSW returned Ok(0), reset recoveries=0
```

The assertion that the command must fail does fail. This establishes a
false success at the block driver's command boundary; it does not claim
that an actual disk lost data during the audit.

USB Mass Storage Bulk-Only Transport requires an exactly 13-byte CSW
and defines invalid-CSW recovery. See [USB-IF BOT 1.0, sections 5.2 and 6.3](https://www.usb.org/sites/default/files/usbmassbulk_10.pdf).

Recommended fix: require `moved == Csw::LEN` before decoding, in both
normal and recovery paths. Treat a short CSW as invalid, record the fault,
and perform Reset Recovery, or halt first in strict mode. Clearing the
buffer alone is insufficient: missing status must never mean success.

Regression coverage should include 0-, 8-, 12- and 13-byte replies, a
previous Passed status, a previous Failed status, the recovery path and
strict mode.

Tracking: [incident 0007](../incidents/0007-ehci-short-csw-accepted.md).

## 2. [P2] A transient directory-list error can erase updater state

Code: [apps/installer/src/main.rs](../../apps/installer/src/main.rs),
`file_size`, lines 75–84; `read_state`, lines 190–194;
`write_state_section`, lines 226–237.

`file_size` returns `None` both when a file is absent and when `fs.list`
fails before finding it. The new `read_state` interprets either result as
a missing file and returns an empty string. A subsequent successful
`write_state_section` replaces the existing `updater/state` with just the
section being written.

This bypasses the intended `inst-state-unreadable` protection: that fault
is only raised after the initial size lookup succeeded. A transient
`ReplyLost` or timeout followed by service recovery can therefore erase
the plan and staged list during the installer's LIST operation.

Reproduction: an existing state contains installed, plan and staged
sections. The first directory-list request fails; opening and replacing
the file then succeed. The extracted production helpers produce:

```text
installer: write accepted=true, state="[installed]\nhello_ext 1\n"
```

The plan is lost, the write reports success, and no unreadable-state fault
is raised. The probe's preservation assertion fails.

Recommended fix: distinguish `Result<Option<size>, FsError>` from
absence, or open the file and recognize only an explicit NotFound as
missing. Propagate every other lookup/read failure and refuse the
read-modify-write. Review other installer callers of `file_size` for the
same error conflation, especially installed-version detection.

Regression coverage should distinguish absent state from a failed list,
failed open and failed read, and verify that unrelated sections survive.

Tracking: [incident 0008](../incidents/0008-installer-state-read-error.md).

## 3. [P2] The updater's global deadline does not bound response headers

Code: [apps/updater/src/main.rs](../../apps/updater/src/main.rs),
`fetch`, lines 690–716;
[libs/http/src/lib.rs](../../libs/http/src/lib.rs), `fetch_with`, lines 402–425;
[sdk/https/src/lib.rs](../../sdk/https/src/lib.rs), `get_with`.

The new ten-minute run deadline is checked before starting a download and
inside its body sink. The timeout passed to the transport is fixed for
each network operation. Header parsing and informational responses do not
call the sink.

A source can send a small `103 Early Hints` response periodically, always
before the per-operation timeout. The HTTP parser discards each interim
header and waits for another. No cumulative byte limit or absolute
deadline stops this phase, so the source can hold `update` indefinitely.
It needs no signing key: verification has not started yet. Chunk framing
and trailers likewise need an absolute transport-level deadline rather
than relying solely on delivery of body bytes.

Reproduction: a simulated transport advances time by one second per
receive, supplies 700 informational responses, then a zero-length final
200 response. Each receive takes less than the 15-second operation
timeout. The production HTTP parser finishes with:

```text
HTTP: Ok(200), elapsed=701000ms, deadline=600000ms, sink calls=0
```

The deadline assertion fails. This is a simulated-clock reproduction; the
audit did not wait ten real minutes against an adversarial network server.
An infinite stream is inferred from the same unbounded loop.

Recommended fix: carry an absolute deadline through DNS, connect, TLS and
every send/receive. Recompute each operation's remaining budget and abort
when it is exhausted. A separate informational-response count limit can
provide additional protection, but does not replace the run deadline.

Regression coverage should include slow headers, repeated 1xx responses,
chunk framing without body delivery, trailers and TLS handshake progress.

Tracking: [incident 0009](../incidents/0009-updater-header-deadline.md).

## Prior findings and scope boundaries

The earlier Docker `LD_PRELOAD` architecture finding is resolved in
`5589906`, included in this reviewed commit. The same-path checkout mount
fix `ddb6727` is also included. The earlier finding is not counted again.

[Incident 0004](../incidents/0004-dma-mapping-outlives-buffer.md) remains
open: CPU mappings can outlive their DMA backing object's ownership,
and device teardown without an IOMMU needs a separate lifecycle fix.
This predates the reviewed range. Passing IPC and process-reaping tests
does not resolve it; no new hardware or use-after-free reproduction was
performed here.

The review checks the update trust chain, version policy, state exchange,
IPC capability accounting and peer-close integration, USB recovery,
boot self-test gating, signing tooling and Docker changes. The release's
ADRs and prior audit resolutions are treated as contracts to verify, not
as proof that their implementations are correct.

The full QEMU suite covers nominal and injected-failure paths, including
the new IPC, EHCI, update and no-selftest scenarios. It does not establish
correct behaviour for every malformed device response, real firmware,
hub/transaction-translator topology, controller timing, power loss or ARM
Docker host. No real hardware, physical power-cut, ARM-host or private
release-key test was performed. No independent multi-reviewer audit was
performed in this session.

## Disposition

The three findings above are open. The official suite is green, but that
does not justify declaring the release free of these defects. Prioritize
the EHCI false-success path, then state preservation and the downloader's
absolute deadline. Keep the reproductions as regressions when fixing them,
and follow the failure protocol before closing their incidents.

## Resolution (2026-10-18)

All three findings were fixed on `develop` the same day, each on its own
branch with host regressions and QEMU scenarios, each audited twice by
independent reviewers before merging (the first audit of finding 1 caught
a P0 in the xHCI part of the fix, confirmed by a QEMU run, before it could
reach `develop`). Related defects found by those audits were fixed in the
same branches or opened as incidents:

- finding 1: [incident 0007](../incidents/0007-ehci-short-csw-accepted.md)
  closed; the xHCI driver had the same omission and also ignored the data
  residue, [incident 0010](../incidents/0010-xhci-data-residue-ignored.md),
  closed in the same branch;
- finding 2: [incident 0008](../incidents/0008-installer-state-read-error.md)
  closed, with the same discipline applied to the updater and the shell
  history writers; the file service's descriptor table that is never
  reclaimed for a dead client is
  [incident 0011](../incidents/0011-arifs-descriptors-not-reclaimed.md), open;
- finding 3: [incident 0009](../incidents/0009-updater-header-deadline.md)
  closed, including the TLS record loop the first fix had left unbounded
  ([ADR 0033](../decisions/0033-http-fetch-budget.md)).

Integrated tree (develop 397430d): `cargo xtask check` green; full QEMU
suite 153/153 with 1 CPU and 153/153 with 4 CPUs. Hardware verification
of the xHCI changes (bytes-moved accounting, ISP only on IN transfers) on
the laptop is pending and recorded in incidents 0007 and 0010.
