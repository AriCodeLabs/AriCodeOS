# Performance and resource-efficiency audit

Date: 2026-10-23. Snapshot: `731c398` (0.13.0 plus entropy diagnostics,
parallel tests and the fixes from the previous audit).
Audit worktree: `/home/serverbig/AriCodeOS-perf-731c398`, branch
`audit/performance-731c398`.

## Assessment

AriCodeOS already contains useful resource optimizations and good shared
components, but it cannot yet be described as comprehensively optimized.
Its strongest existing improvements are batched filesystem I/O, blocking
filesystem waits, bounded and reused DMA mappings, and shared network,
protocol and runtime libraries. Remaining costs concern wakeup design,
measurement accuracy, eager memory reservations and full-screen rendering
more than duplicated source code.

This is a performance audit, not an optimization patch or a release
certification. Evidence is labeled as guest measurement, native host
microbenchmark, binary inspection or source analysis. No improvements to
production algorithms were applied. Hardware power, physical NIC
throughput and real USB-storage latency were not measured.

## Reproducibility and scope

[Evidence and commands](731c398-performance/README.md) include an isolated
benchmark patch, two scenarios, host probes, raw logs and an ELF inventory.
The working checkout was left untouched. The guest probes ran one at a time during the CI resting interval,
after the other QEMU runners finished.

Final host timings use the same final initrd after the guest suite completed.
A preliminary run with another QEMU suite active is retained separately and
is not the table below. Native timings illustrate scaling only: CPU frequency
and placement were not pinned, and independently timed columns need not add
up. Deterministic pixel counts and ELF sizes do not depend on scheduling.
Guest results are from QEMU TCG, not bare-metal hardware, and do not support
an energy-consumption claim.

## Existing optimizations worth keeping

| Area | Existing behavior | Why it helps |
| --- | --- | --- |
| Filesystem IPC | fsd waits on all service/session endpoints | Avoids the former unconditional 10 ms main-endpoint delay |
| Block I/O | Eight-sector batches for aligned 4 KiB operations | Replaces eight block RPCs with one read request |
| Durability | Atomic replace journal with explicit flush ordering | Reducing flushes blindly would break the persistence contract |
| Buffer lifetime | Bounded `ClientBuffers<8>` and reusable virtual ranges | Bounds retained dead-client buffers and avoids monotonic mapping growth |
| Network | One `net-core` implementation for virtio and Realtek | Fixes and protocol logic are shared across drivers |
| Fairness | Bounded RX and IPC rounds | Stops packet floods from starving local requests and timers |
| Code generation | Release LTO, one codegen unit, dead-code removal | Unused runtime heap disappears from several service binaries |
| Idle | An actual `hlt` path exists | Threads can sleep instead of continuously polling in user space |

## Deterministic I/O and capacity observations

A counted in-memory block device exercising the actual AriFS code gives:

| Operation | Read requests / bytes | Write requests / bytes | Flushes |
| --- | ---: | ---: | ---: |
| Aligned 4 KiB read | 1 / 4096 | 0 / 0 | 0 |
| 4 KiB read at offset 1 | 3 / 4608 | 0 / 0 | 0 |
| Atomic 4 KiB replace | 3 / 8704 | 5 / 9728 | 3 |

[Raw counts](731c398-performance/io-counts.txt). These count library/block
requests, not physical disk operations after host or device caching.
The replace amplification includes the journal, its validation and metadata;
it is not justification to remove durability barriers. The older performance
document's approximate request count should not substitute for these counts.

Some small limits are deliberate resource/feature tradeoffs:

- `libs/net/src/tcp.rs` fixes send and receive buffers at 4096 bytes each.
  With 4 KiB of data in flight, the idealized window/RTT ceiling is about
  400 KiB/s at 10 ms RTT, or 40 KiB/s at 100 ms RTT, before protocol/IPC
  costs. These are analytic bounds, not measured transfer rates. Higher
  throughput requires revisiting buffer budgets along with wakeups.
- `net-core` has eight total TCP slots, including listeners and connection
  states; `sshd` services one connection at a time. They are adequate for
  small workloads, not evidence of broad concurrent-server scalability.
- Each online CPU runs a periodic 100 Hz APIC timer, and several drivers
  wake on 10 ms timeouts. `hlt` alone does not establish low battery use.
  Deadline-driven waits and eventually a one-shot idle timer are candidates;
  power savings require actual hardware measurements.

## Findings and optimization opportunities

### A. Confirmed idle overcount on the single-CPU control

Source: [scheduler idle loop](../../kernel/src/task/scheduler.rs), lines
214–229, and [APIC timer dispatch](../../kernel/src/arch/x86_64/apic.rs),
lines 205–213.

The idle loop records TSC immediately before `sti; hlt` and after returning
from the interrupt. The timer handler can schedule another thread before
returning to the interrupted idle context. When the idle context eventually
resumes, the entire interval is added to `idle_cycles`, including execution
of that other thread. This makes the current percentage unsuitable as a
standalone proof of CPU or power efficiency.

The audit adds a control that remains runnable for 500 ms and then sleeps
200 ms, with raw idle and elapsed counters before and after. The one-vCPU
case distinguishes genuine sleep from scheduling inside the handler.

| Warm control | Reported aggregate idle | Maximum compatible with busy interval |
| --- | ---: | ---: |
| 1 vCPU | 105.23% | 28.94% |
| 4 vCPUs | 81.86% | 82.24% |

For one vCPU, elapsed cycles were 2,681,794,254, the continuously runnable
interval lasted 1,905,633,120 cycles, and the idle delta was 2,822,019,004
cycles. That is incompatible with correct accounting; the first run also
reported 105.50%. Small counter observation offsets cannot explain the
roughly 76-percentage-point excess. The four-vCPU control did **not** show
that aggregate overcount on these runs; the source defect depends on the
wake/preemption path and should not be reported as reproduced on every CPU
configuration. Counters accumulate completed idle intervals, so interval
boundary attribution also needs a defined sampling contract.

Recommended direction: end idle accounting on interrupt entry, before a
handler can switch threads, or implement scheduler state accounting whose
idle interval ends before switching away. Define whether interrupt service
time is idle or active and test that definition. Retain per-CPU timestamps
and regression cases with timed wakeups, sustained load and SMP. Merely
clamping displayed percentages to 100 does not fix attribution.

### B. Network RPC waits for a NIC interrupt or periodic timeout

Source: [net-core run loop](../../services/net-core/src/lib.rs), lines
2067–2095; [IRQ wait](../../kernel/src/hw.rs), lines 61–68.

The service polls up to eight IPC requests with timeout zero, then waits
only on its NIC IRQ for up to 10 ms when no RX frames remain. A request
arriving after that poll does not satisfy the IRQ wait condition. Local
metadata requests such as `NetClient::info` therefore inherit timer-scale
latency despite requiring no network traffic. Pending IPC can also remain
queued after the eight-request budget while the service sleeps.

Measured warm network-info p50 is 10,002 µs on one CPU and 10,001 µs on
four CPUs, versus filesystem-list p50 of 58 and 64 µs. These are different
service operations, not an isolated IPC microbenchmark, but the timer-sized
plateau in a metadata-only request supports the inspected wakeup mechanism.

Related patterns exist in virtio-input and the USB input service. The
compositor additionally reads input devices sequentially with nominal 1 ms
timeouts; that is not a guarantee of 1 ms responsiveness with a 100 Hz
scheduler tick and a driver paced by a 10 ms IRQ wait.

Recommended direction: a shared wait-set mechanism for IRQ, IPC and the
next timer deadline. Preserve bounded RX/IPC rounds, but continue immediately
when work remains. This is a useful performance-driven factorization for
multiple drivers. Reducing a constant or replacing the wait with a spin
would exchange latency for CPU usage without fixing the wakeup model.

### C. Full-screen output and unconditional diagnostics on pointer movement

Source: [compositor](../../services/compositor/src/main.rs), `on_input`,
`Screen::flip` (81–94) and `compose` (318–365).

Moving the pointer sets one global `dirty` flag. Composition rebuilds the
desktop and `flip` writes every pixel to the framebuffer using volatile
stores. Every composed frame also prints a frame line and samples of each
window, including in ordinary GUI use.

The production graphics-library probe moved the pointer by one pixel on an
empty desktop:

| Resolution | Pixels actually changed | Pixels written by current flip | Framebuffer bytes per flip |
| --- | ---: | ---: | ---: |
| 1024 × 768 | 80 | 786,432 | 3,145,728 |
| 1920 × 1080 | 80 | 2,073,600 | 8,294,400 |

These are deterministic counts, not measured FPS. At an assumed 60 updates
per second, the current 1080p flip alone would write about 475 MiB/s,
before composition and framebuffer reads/conversion. This does not claim
the current GUI achieves 60 FPS. Real UART output is also finite: COM1 is
configured for 115200 8N1 and `write_byte` busy-waits. QEMU does not model
that cost as a physical display/serial device necessarily would.

Recommended direction: dirty rectangles for old/new cursor bounds and
changed windows; clipped composition/flush; coalesce updates to a display
cadence. Put per-frame pixel samples and tracing behind the runtime test
or diagnostic mode. Measure bytes flushed, composition time and frame
latency before adding SIMD or changing volatile/MMIO semantics.

### D. Fixed runtime arenas and large network stack frames

Sources: [runtime heap](../../sdk/runtime/src/lib.rs), lines 25–39;
[process loader](../../kernel/src/user/process.rs), lines 206–252;
[network run stack](../../services/net-core/src/lib.rs), line 2024.

The user allocator owns a static 256 KiB arena. When the binary retains
that allocator, the loader allocates and clears all PT_LOAD pages eagerly,
including its BSS, before the process begins. This is real physical backing,
not only reserved virtual address space. Each process also receives a
64 KiB user stack and a 32 KiB kernel stack.

The [ELF inventory](731c398-performance/elf-inventory.csv) separates
loadable pages from debug-rich file sizes:

| Binary | Loadable pages | Runtime arena included | User + kernel stack |
| --- | ---: | ---: | ---: |
| virtio_net | 344 KiB | 256 KiB | 96 KiB |
| virtio_input | 280 KiB | 256 KiB | 96 KiB |
| shell | 568 KiB | 256 KiB | 96 KiB |
| fsd | 40 KiB | 0 | 96 KiB |
| compositor | 28 KiB | 0 | 96 KiB |

DMA, framebuffer/back buffers, page tables and kernel process metadata
are additional; this table is not RSS and does not measure how much of an
arena is actively used. The manifest's `memory` field limits DMA buffers,
not these ELF and stack allocations. LTO already eliminates the allocator
in services that do not use it; applying a 256 KiB charge to every program
would be incorrect.

Binary inspection also confirms that `run::<virtio_net::Nic>` reserves
44,952 bytes for its local stack frame, plus saved registers and return
address, before its callees. The existing
[incident 0018](../incidents/0018-net-driver-stack-headroom.md) documents
the deeper release/dev paths. This audit confirms the release prologue;
it does not remeasure every call path or reproduce a dev-build overflow.

Recommended direction: instrument allocation/stack high-water marks first;
then choose per-program arena budgets or on-demand backing with an explicit
OOM policy. Move the network state into stable off-stack storage with
construction in place. A naive `Box::new(Stack::new(...))` can still create
a large stack temporary; verify generated frames. Do not simply increase
every stack to accommodate one service.

### E. Scheduler and IPC bookkeeping scale beyond the useful work

Sources: [scheduler reap](../../kernel/src/task/scheduler.rs), lines
395–419; [policy terminated](../../libs/sched/src/lib.rs), lines 299–305;
[IPC notifications](../../kernel/src/ipc.rs), lines 168 and 211–237.

Every resumed context switch calls `reap`, which takes the shared scheduler
lock and scans all thread states for terminated threads even when none
exist. Sleeper expiration also walks a vector on each BSP tick. In the IPC
layer, every send wakes the global `ANY_RECEIVERS` queue, including waiters
whose endpoints have no new message. Those receivers can run and re-check
unrelated queues. These are source-confirmed scalability costs; their
whole-system contribution has not been isolated by a kernel profile.

Native host timings for the real scheduling policy (median of seven
batches, no locks or hardware context switches):

| Threads | Empty terminated scan | Yield alone | Yield plus scan |
| ---: | ---: | ---: | ---: |
| 16 | 35 ns | 29 ns | 64 ns |
| 64 | 140 ns | 34 ns | 186 ns |
| 256 | 585 ns | 20 ns | 324 ns |
| 1024 | 1155 ns | 30 ns | 1209 ns |
| 4096 | 4737 ns | 50 ns | 4738 ns |

[Raw native results](731c398-performance/host-results.txt). The columns
were timed independently; host noise is visible, especially at 256 threads.
These timings illustrate growth and are not a claim of a corresponding
speedup for the OS. Current small service counts reduce the practical
urgency compared with the network wakeup delay.

Recommended direction: enqueue terminated TIDs at exit and consume that
queue; notify receive-any waiters registered on the relevant endpoints;
measure lock hold/wait times. Consider ordered deadlines when sleeper
counts justify it. Per-CPU ready queues and allocator size classes should
follow contention/fragmentation evidence, not precede it.

### F. Initrd lookups repeatedly validate unchanged metadata

Source: [initrd find](../../kernel/src/initrd.rs), lines 67–69, and
[library parser](../../libs/initrd/src/lib.rs), lines 46–65.

The kernel keeps the raw immutable initrd, then calls `Initrd::parse` for
every lookup. Parsing validates all entries, followed by another linear
search. The observed image contains 74 files. In the native host probe,
lookup of `shell` costs 1688 ns with revalidation, 647 ns when retaining a
parsed view, and 38 ns with a separately built BTreeMap index.

This is a small, bounded optimization opportunity for boot/spawn, not a
major steady-state bottleneck. The index comparison is an experimental
alternative in the probe. Retain a validated view or build an index once
at mount. Include index memory and ELF copying in any startup benchmark;
lookup improvements do not imply the same speedup for process creation.

### G. Current performance tests check output, not performance

Source: [perf scenario](../../tests/qemu/perf_bench.toml), lines 11–32,
and [performance documentation](../performance.md).

The scenario requires percentile labels and the string `% idle`; it has
no latency or idle-value assertion. It invokes `bench` once even though
the documentation asks for two runs and retaining the second. The recorded
baseline is from version 0.7 and covers syscall, filesystem IPC and 4 KiB
file operations, leaving network metadata latency, render work, per-process
memory and scheduler contention unobserved.

The benchmark uses plain `rdtsc` around tiny operations. It does not
serialize the samples or identify CPU migration; keep this limitation in
mind before drawing nanosecond conclusions on SMP hardware. The kernel
clock assumes a shared invariant TSC as well.

Recommended direction: a dedicated serial performance job with a fixed
QEMU/CPU configuration, warm-up and repeated samples; record percentiles
and compare to the same environment's baseline with justified tolerances.
Add control workloads that validate the counters themselves. Track per-
service allocations, retained DMA bytes, stack peaks, wakeups, context
switches, IRQ time, bytes read/written and bytes flushed to the display.
Hardware power and throughput need separate on-device measurements.

## Factorization assessment

Factoring is already a strength in `net-core`, protocol/ABI crates, `rpc`,
`ClientBuffers`, the allocator, filesystem and scheduler policy. Release
static linking means sharing source does not automatically share executable
pages or static state between processes. LTO and binary inspection provide
better evidence of resource impact than source-line counts.

Recommended order:

1. Share the IRQ/IPC/deadline wait-set abstraction across service loops;
   this addresses a measured workload and reduces repeated polling logic.
2. Add shared measurement helpers and a machine-readable benchmark result
   format, while preserving correct per-CPU and per-service accounting.
3. Encapsulate bounded session bookkeeping where fsd and netd truly share
   semantics; retain their different ownership and failure behavior.
4. Split USB service files into transport, device state/recovery and service
   dispatch modules for reviewability. Their size alone is not evidence of
   runtime waste, and xHCI/EHCI hardware behavior should stay explicit.
5. Treat repeated formatting helpers as low-priority maintenance work.
   Deduplicating them is unlikely to beat fixing timer waits or full-frame
   writes; use a dependency appropriate to the domain rather than importing
   an entire service library to format one address.

Do not remove durable flushes, timeout ownership protections, RX budgets
or capability validation to improve a benchmark. These are correctness
properties; optimization must preserve them.

## Suggested implementation sequence

| Order | Work | Acceptance evidence |
| --- | --- | --- |
| 1 | Correct and validate CPU accounting; preserve a warmed baseline | A runnable busy interval is excluded from idle on 1 CPU and from aggregate idle on SMP |
| 2 | Wake services on IPC/IRQ/deadline and avoid sleeping with queued work | Network metadata RPC loses the timer-sized delay; idle wakeups and fairness remain bounded |
| 3 | Resolve known network stack headroom and measure arena usage | Generated frames and tested deepest paths fit the chosen budget; per-process peaks inform arena sizes |
| 4 | Add dirty-region rendering and gate frame diagnostics | Pointer-only updates flush bounded cursor regions; visual correctness and input latency remain covered |
| 5 | Replace reap scans/global notifications with targeted work | Kernel counters and scaling tests show lower scan/wakeup/lock costs |
| 6 | Cache initrd metadata and perform targeted module refactoring | Startup measurements include index cost; behavior and ownership tests remain unchanged |

Orders 1–4 address the current observable behavior or known resource
risk. Order 5 becomes more valuable as the workload grows. Order 6 is
useful maintenance and a modest startup optimization. Overall application
speedup remains unmeasured; track each cost independently. All findings
remain open in the audited snapshot; this report applies no production fix.
