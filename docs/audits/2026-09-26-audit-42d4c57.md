# AriCodeOS audit

Date: 2026-09-26. Reviewed commit: `42d4c57`.
Scope: the seven workspace crates, build configuration, boot protocol, documentation and QEMU scenarios. Static review and local checks. No versioned code was modified.

The nominal M0 boot works in the tested environment. Five defects were found: two high priority and three medium priority. The current suite passes, but does not cover these cases.

## Validation performed

- `cargo xtask check`: passes; formatting and Clippy for the seven crates.
- `cargo xtask test --all`: 18 unit tests and 4 QEMU scenarios pass.
- Additional ELF test with release arithmetic: reproduces an incorrect reservation range; the out-of-bounds write was not executed.
- QEMU with the original ELF and only `e_entry = 0`: CPU exception and timeout after 8 seconds.
- `cargo xtask test --area booot`: exits with code 0 and "0 QEMU scenarios, 0 failed".

## 1. High: ELF overflow allows copying outside the kernel reservation

Location: `libs/elf/src/lib.rs:105` and `:131`; used in `boot/src/main.rs:92` and `:100`.

The parser checks the file bounds, but not that `vaddr + memsz` and its page rounding are representable. `virt_range()` uses unchecked additions. With overflow checks disabled in release, the upper end can wrap to zero and drop out of the computed maximum. The subsequent copy trusts that range.

Reproduction with two segments accepted by the parser:

- First: `vaddr=0xffffffff80000000`, `filesz=memsz=1`.
- Second: `vaddr=0xfffffffffffffff8`, `filesz=memsz=8`.
- Result: range `0xffffffff80000000..0xffffffff80001000`; a 4096-byte reservation, but the second copy has an offset of 2147483640 bytes.

The reproduction confirms the invalid computation. The consequence inferred from the copy code is a write outside the reservation or an exception, depending on the physical map. It requires a corrupt or tampered kernel ELF; no remote exploitation path is demonstrated.

Fix: validate additions and rounding with checked arithmetic; reject invalid ranges before reserving; also check that each destination and length fit in the reservation. Add regressions for overflow, the extremes of the virtual address space and overlapping segments.

Evidence: `build/audit/elf_probe.rs` and the executable `build/audit/elf_probe`. The library for this test was built from the original code with `-C overflow-checks=no`.

## 2. High: the safe paging API does not guarantee memory safety

Location: `libs/x86-paging/src/lib.rs:37`, `:47`, `:60` and `:64`.

`PagePool::new` is a safe function that writes `pages * 4096` bytes through a `NonNull<u8>` whose type guarantees neither the size, alignment, exclusivity nor lifetime of the reservation. For example, `PagePool::new(NonNull::dangling(), 1)` is a call allowed without `unsafe`, even though it would write to invalid memory.

In addition, `PageTables.pml4` is public and mutable: a caller can insert a PRESENT entry with an arbitrary address and then make `map_4k`, also safe, dereference it. The `&'static mut` references are not tied to the lifetime of the reservation either.

Impact: undefined behaviour from code that uses only the safe interface. No corruption has been observed on the current nominal path, which uses pages reserved by UEFI. Finding by inspection; no deliberately invalid accesses were executed on the host.

Fix: represent the ownership and lifetime of the storage, or require an `unsafe` constructor with an explicit contract; make the tables private and restrict modifications that break their invariants. Also review the public flags that are copied directly into the entries.

## 3. Medium: the loader jumps to an unvalidated ELF entry point

Location: `libs/elf/src/lib.rs:81` and `boot/src/main.rs:225`.

Any `e_entry` is accepted, without requiring it to belong to an executable PT_LOAD segment. The base address check does not prevent this.

Reproduction: copy the built kernel and change only the eight bytes of `e_entry` to zero. AriBoot logs `entry 0x0`, runs ExitBootServices and ends in a firmware `#UD` exception. QEMU does not produce the controlled code-35 failure and reaches the 8-second timeout.

Fix: check that the entry point lies within the valid range of an executable segment before leaving boot services. Add scenarios for a null entry, one outside the segments and one inside an NX segment.

Evidence: `build/audit/entry-zero/serial.log` and the modified ELF in its `esp` subdirectory.

## 4. Medium: scenario names allow deleting outside their directory

Location: `tools/xtask/src/scenario.rs:95` and `tools/xtask/src/image.rs:36`.

`Scenario.name` is loaded without restricting path components and is then joined with `build/scenarios`. The function runs `remove_dir_all` on the resulting path before copying the ESP. An absolute name replaces the prefix and a name with `..` can escape the intended directory. For example, `/tmp/otra-carpeta` would direct the deletion to `/tmp/otra-carpeta/esp`.

Impact: loss of an `esp` directory unrelated to the scenario and writes outside `build/scenarios`, with the user's permissions. It requires a modified TOML; the four current names are valid. Finding by inspection, without running external deletions.

Fix: accept only simple identifiers with a restricted character set; reject absolute paths, separators and `.`/`..` components before any file operation. Keep the destination inside the scenarios directory and take pre-existing symbolic links into account.

## 5. Medium: test filters can report success without integration

Location: `tools/xtask/src/test.rs:24` and `:74`.

If no scenario matches the requested area or level, the runner leaves `failed` empty and returns success. A typo can produce an apparent validation without booting QEMU. The same happens with `--area panic` at the default smoke level, since the only scenario in that area is full.

Reproduction: `cargo xtask test --area booot` exits with code 0 after printing "0 QEMU scenarios, 0 failed".

Fix: for the smoke/full levels, return an explanatory error when the selection is empty. Show the available areas and warn if the area's scenarios require another level. Keep the intentional behaviour of the unit level.

Evidence: `build/audit/empty-filter.log`.

## Scope and documented debt

The RWX physical map and the lack of our own GDT/IDT are already listed as M0 debt in `docs/architecture.md`; they are not presented as new defects. Capabilities, isolated processes and user-space drivers belong to the roadmap, not yet to the audited implementation.

Integration verification covers QEMU q35, the qemu64 CPU, 512 MiB and the environment's OVMF, in release. Real hardware, other firmware and the debug profile were not tested. Dependencies were not checked against a CVE/RustSec database, and this review is not equivalent to an exhaustive proof of the absence of vulnerabilities.

Proposed priority: first fix the ELF bounds and the paging invariants; then validate the entry point and harden the scenario runner.

# Resolution (branch `fix/audit-42d4c57`)

| # | Finding | Fix | Regression |
|---|---------|-----|------------|
| 1 | ELF overflow | `Elf::parse` validates `vaddr + memsz` and its page rounding with checked arithmetic (`AddressOverflow`), rejects overlapping segments (`OverlappingSegments`) and ELFs without segments; `virt_range` and `page_range` can no longer wrap. AriBoot also checks each copy against the real reservation. | `libs/elf`: `rejects_address_overflow`, `rejects_overlapping_segments`, `rejects_no_segments` |
| 2 | Unsafe paging API | `PagePool::new` is `unsafe` with a documented contract; `PageTables.pml4` is private; every dereference goes through `PagePool::table`, which requires the address to belong to the pool; leaf flags are masked (`LEAF_FLAG_MASK`); `map_4k` requires alignment and does not descend through large pages. | `libs/x86-paging`: `leaf_flags_cannot_smuggle_address_bits`, `map_4k_over_2m_page_panics`, `map_4k_rejects_unaligned` |
| 3 | Unvalidated entry point | `Elf::parse` requires `e_entry` to fall inside an executable `PT_LOAD` segment (`EntryOutsideText`). AriBoot fails before `ExitBootServices` with its own message. | `libs/elf`: `rejects_entry_outside_executable_segment`; QEMU: `boot.loader_rejects_bad_entry` (injection `patch_entry = 0`) |
| 4 | Scenario names | `scenario::validate_name` only allows `[a-z0-9._-]`, without `..` or a leading `.`; it is applied when loading the TOML and again in `image::scenario_dir` before deleting. | `xtask`: `scenario_names_cannot_escape_scenarios_dir` |
| 5 | Empty filter = success | `scenario::select` returns an error for smoke/full if there are no scenarios, listing the known areas and the ones that would be included with `--all`. | `xtask`: `empty_selection_is_an_error_for_qemu_levels` |
