## 1. [P2] Update servers can take ports reserved for QEMU by the same suite

Code: [tools/xtask/src/qemu.rs](../../tools/xtask/src/qemu.rs),
`UpdateServer::start`, lines 605–609; related code:
[ports.rs](../../tools/xtask/src/ports.rs), lines 35–58, and
[test.rs](../../tools/xtask/src/test.rs), lines 250–254 and 377–378.
Introduced by `c0c1bac`.

`PortLease::take` chooses free ports and remembers them in `LEASED`, but
closes its temporary listeners before returning. That permits QEMU and
OpenSSL to bind the ports later. Other leases consult `LEASED`, protecting
against reuse within the suite.

`UpdateServer::start` instead binds port zero directly and never consults
`LEASED`. The kernel can therefore assign a port that another scenario,
or this same scenario, has reserved but has not bound yet. The runner
allocates its forwards before publishing and starting the update server,
so this window exists even with `--jobs 1`; parallel runs enlarge it.
When QEMU subsequently binds its `hostfwd`, it fails with an occupied
port. An update server can similarly steal a pending HTTPS port.

The probe held 64 two-port leases and started the actual update-server
implementation. The first server allocation in the observed run took a
leased port:

```text
PORT COLLISION: update server took leased port 36201 after 1 allocations; forward bind: Address already in use (os error 98)
```

The sample amplifies the allocation window; it does not measure the
frequency in a normal suite. It proves that the same process can violate
its port-reservation contract, without an unrelated process competing.
The existing tests verify leases against other leases and update servers
against other update servers, but never the two together.

Recommended correction: route update-server allocation through the same
reservation mechanism. Prefer an allocator that returns both a retained
listener and its lease, selecting and registering the port under the
shared protocol. Keep the reservation for the server's lifetime and
exclude pending QEMU/HTTPS leases. Add a regression mixing both kinds of
allocation. This addresses the internal collision; the separately
documented race with unrelated host processes remains a distinct issue.

Resolution: **open**.

## 2. [P2] CI reuses report directories and overwrites earlier run evidence

Code: [tools/docker/ci/ci.sh](../../tools/docker/ci/ci.sh), lines 112–114;
related writes at lines 86, 90, 98–102 and 155–158.
Introduced by `c0c1bac`; the duration fix in `8366576` does not address it.

The report directory consists of the UTC minute, sanitized branch name
and short commit hash. `mkdir -p` accepts an existing directory. Two
one-shot invocations for the same branch and commit starting within one
minute therefore share the same report directory. Fast failure/retry
runs and `--quick` invocations can meet this condition.

`step` truncates the old command logs but appends to `steps.txt`.
`collect` replaces result lists while leaving older failed-scenario
artifacts. Finally, `summary.txt` is overwritten and both `index.txt`
entries point to the same directory. The result is a mixture of two runs
and loss of the original top-level failure report.

The probe simulated two quick invocations in one minute, the first
failing and the second passing:

```text
CI REUSE: first exit=1, second exit=0, same directory=yes
Index entries: 2
Accumulated step entries: 4
AriCodeOS continuous run: PASS
```

The final summary contained both FAIL and PASS step entries and retained
the previous failed scenario's files. The first run's summary and command
logs had been replaced. The defect concerns evidence retention and
attribution: it does not claim that the second invocation's exit code
misrepresents its own simulated commands.

Recommended correction: atomically create a fresh directory for every
invocation, for example with `mktemp -d` under `/reports` using the current
prefix plus a random suffix. Keep `latest` and `index.txt` pointing to the
unique directory. Seconds alone do not guarantee uniqueness. Add a
regression with two runs sharing the same clock/commit, checking that
both summaries, logs and failed artifacts remain separate.

Resolution: **open**.

## Existing risks and review limits

- [Incident 0018](../incidents/0018-net-driver-stack-headroom.md) already
  tracks insufficient network-driver stack headroom, including a static
  dev-build path exceeding 64 KiB. It is an existing open issue, not a
  new finding from this audit; its stack measurements were not repeated.
- ADR 0039 exposes the existing weak entropy fallback; it does not replace
  it with a hardware source. Reporting a source and counting samples do
  not establish an entropy estimate. This review found no additional
  confirmed defect in the changed entropy code, but did not validate it
  on hardware or execute its QEMU scenarios.
- The 62 passing host tests and targeted Clippy check do not constitute a
  whole-system release certification. Results from the separate running
  QEMU suite are not included in this audit's validation counts.
