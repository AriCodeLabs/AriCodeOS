## 1. [P1] A non-xHCI USB controller hangs init's boot

Code: [services/init/src/main.rs](../../services/init/src/main.rs),
lines 782–796, especially the endpoint publication in 793–796.
Related paths: `Controller::open` in
[services/usb-input/src/main.rs](../../services/usb-input/src/main.rs),
lines 192–208; `InputClient::call` in
[sdk/rust/src/input.rs](../../sdk/rust/src/input.rs).

The selection checks only class/subclass `0c.03`. It therefore also
launches `usb_input` for pre-xHCI USB controllers. After
creating the process, init adds its endpoint to `input_eps` without waiting for
the service to be ready or checking whether the driver exited.

In the reproduction, `-device usb-ehci,id=review_ehci` was added to the
`usb.hid_boot` scenario, keeping the xHCI, the keyboard and the mouse. The
EHCI controller is claimed and its driver exits with code 10: the `bar_handle`
helper also requires an MSI-X IRQ, which that device lacks. The real xHCI
does initialize correctly. However, `input_client` is left
waiting for the `Info` reply from the exited driver's endpoint. The IPC
wait is unbounded, and AriInit in turn waits for the client. The
system-ready marker never appears and the boot services do not complete.

Evidence:

```text
pci: 00:06.0 8086:24cd claimed
usb-input: xHCI initialization failed
user: process 16 'usb_input' exited with code 10
input_client: device 0: QEMU Virtio Keyboard
input_client: device 1: QEMU Virtio Mouse
usb-input: device ready: USB HID Keyboard+Mouse
[FAIL] audit.usb_legacy ... timeout 90s
```

Exiting with 0 in the `NOT_XHCI` branch would not fix the endpoint published
without a server either. PCI identification must include Programming Interface
`0x30`, defined for xHCI in section 5.2.2 of the
[xHCI specification](https://www.intel.com/content/dam/www/public/us/en/documents/technical-specifications/extensible-host-controler-interface-usb-xhci.pdf).

Proposed fix: filter for the correct type before starting the driver and
publish only services whose initialization has completed. An
early exit must not leave a client blocked on an orphaned endpoint.
Regression: boot with EHCI and xHCI present, checking that
`ARICODEOS_KERNEL_READY` is reached and that xHCI input remains available.

## 2. [P2] The FS/LS interrupt interval is rounded in the wrong direction

Code: [libs/xhci/src/lib.rs](../../libs/xhci/src/lib.rs), lines 507–519.
Used in `Controller::enumerate_port`, when creating `EndpointContext::interrupt_in`.

The loop computes the ceiling of `log2(bInterval * 8)`. For low/full-speed
interrupts, xHCI requires rounding down and limits the
Interval field to 3–10. See section 6.2.3.6, table 6-12 and note 113 of the
[xHCI specification](https://www.intel.com/content/dam/www/public/us/en/documents/technical-specifications/extensible-host-controler-interface-usb-xhci.pdf).

The tests call the reviewed commit's function directly:

```text
bInterval=255, programmed_interval=11, maximum_valid=10
bInterval=10ms, programmed_period=16ms
```

In the first case a field outside the allowed range is written; a
controller that validates it may reject `Configure Endpoint`. In the
second, a 16 ms poll is programmed where 8 ms is correct. The host
test confirms the generated values, not a real hardware response.

Proposed fix: use round-down for FS/LS and keep the
current conversion for HS/SS. Regression: include non-power-of-two values
and the valid extremes, especially 10, 129 and 255.

## 3. [P2] The keyboard decoder drops changes and still advances its state

Code: [libs/input/src/lib.rs](../../libs/input/src/lib.rs), lines 313–329
and 358–372. The driver also reserves only 16 elements in
`Controller::handle_transfer_event`.

A change between reports can produce 8 modifier changes,
6 key releases and 6 presses, plus `EV_SYN`: 21 events.
The HID format allows all eight modifier bits and the six key
slots; see appendices B and F.5 of
[HID 1.11](https://www.usb.org/sites/default/files/hid1_11.pdf).

The function only accepts `[Event; 16]`. When it fills up, `push` drops the
remaining events, but `self.keys` and `self.modifiers` advance to the full
report. The lost changes are not delivered when the same report is repeated.

Host reproduction with the real implementation:

```text
Previous report: ff 00 04 05 06 07 08 09
New report:      00 00 0a 0b 0c 0d 0e 0f
events=16, new_presses=2, repeated_report_events=0
```

Four presses and the sync event are missing. The consumer
is left with a state different from the keyboard's, and may later receive
releases for keys whose press it never received.

Proposed fix: accept the maximum of 21 events both in the library
and in the driver's buffer, or explicitly keep the pending ones
before treating the report as consumed. The regression must compare all
events and also check the repeated report and the final release.

## 4. [P2] The full FS descriptor is requested before adjusting the EP0 size

Code: [services/usb-input/src/main.rs](../../services/usb-input/src/main.rs),
lines 457–466; initial EP0 configuration at 427 and adjustment at 470–481.

The initial context of a Full-Speed device uses Max Packet Size 8.
Before finding out its real value, the full 18-byte descriptor is
requested. An FS device whose EP0 supports 16, 32 or 64 bytes may respond
with a packet larger than the one configured in the controller. On a controller
that enforces that limit, enumeration may abort before reaching the
`Evaluate Context` meant to correct it.

Section 4.3, step 7, says to read 8 bytes first, obtain
`bMaxPacketSize0`, update the context and then continue. It is also
described in section 3.3.6 of the
[xHCI specification](https://www.intel.com/content/dam/www/public/us/en/documents/technical-specifications/extensible-host-controler-interface-usb-xhci.pdf).

Proposed fix: split out that initial read for FS and check the
result of `Evaluate Context` before requesting the full descriptor.
Recommended regression: FS device with a 64-byte EP0 and validation of the
request order. This finding comes from reviewing the code and the
controller contract; that physical configuration has not been run.

## Previous audit

Both findings from `3eb4965` are fixed in the reviewed code:

- The process can only be reaped once `release_address_space` finishes
  and publishes `reaped`; the scheduler thread disappearing is no longer enough.
  There are 180-process regressions with one and four CPUs.
- The IOMMU keeps one owner per PCI function, removes the association from the
  previous domain and checks ownership before clearing a context.
  The self-test checks reassignment A → B and the release of both.

The console is built in static storage and receives the
surface afterwards, avoiding the large temporary on the boot stack. The added
RSP read measures usage at that instant; it is not a measurement of the historical
maximum nor a guard page. No new regression from
that fix has been identified.
