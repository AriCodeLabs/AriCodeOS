## 1. [P2] `run` leaks the SYSTEM handle when the program does not exist

Code: [services/shell/src/main.rs](../../services/shell/src/main.rs),
lines 408–434 of `28e745a`, especially the error branches at 429–434.
Contract checked in
[kernel/src/user/syscalls.rs](../../kernel/src/user/syscalls.rs), function
`process_spawn` of the same commit.

The shell duplicates `SYSTEM` with `READ | TRANSFER` before calling
`process_spawn_with`. If the name does not exist in the initrd, the kernel returns
`NotFound` before consuming the handle. The shell's error branch prints the
message but does not close the duplicate. Each failed attempt leaves one
more entry in its handle table.

Impact: repeating nonexistent names reaches the limit of 256 handles per
process. From then on, duplicating `SYSTEM` fails and `run` also rejects
valid applications with `run: no system access`.
The exact number of attempts depends on how many handles the shell has open.

Isolated reproduction performed:

1. Create a 256-entry table with 10 initial handles.
2. Run the `run` function 260 times with `no-existe`, simulating the kernel's
   `NotFound` return without handle transfer.
3. Check that only the 10 initial handles still exist.

Observed result: 256/256 entries occupied; the next duplication
returns `Err(Limit)`. The conservation assertion fails.

Proposed fix for the reviewed implementation: release the duplicate
when creation fails and the handle remains in the parent. Bear in mind
that some error paths of `process_spawn` may have already consumed the
handles; atomic transfer must not be assumed on every exit.

Recommended regression: a QEMU scenario that repeats `run no-existe` more than
256 times and then runs `run hello_app 7`, requiring correct output.
The existing `shell.commands` scenario only tests one nonexistent name,
which is why it passes without detecting the accumulation.

## 2. [P2] `permissions::granted` stops enumerating when it hits a gap

Code: [sdk/rust/src/permissions.rs](../../sdk/rust/src/permissions.rs),
lines 38–43 of `28e745a`.

The walk over extra handles ends with `None => break`. Handles delivered at
startup are contiguous, but may stop being so when the program closes or
transfers one of them. Finding an invalid handle does not imply that later
ones no longer exist.

Impact: an application that gives up a permission may stop discovering
other permissions that are still available through this API. This does not revoke
the skipped handles: the enumeration simply stops reflecting those still valid.

Isolated reproduction performed:

1. Simulate the three initial handles, an `ENDPOINT` at `0x10004` and a
   `SYSTEM` at `0x10005`.
2. Check that `granted` enumerates all five.
3. Close `0x10004` with `drop_handle` and repeat the walk.

Observed result: only the three basic handles are enumerated, although
`permissions::is(Handle(0x10005), kind::SYSTEM)` still returns `true`.
The assertion requiring `0x10005` to appear in the result fails.

Proposed fix: continue the walk up to `MAX_EXTRA`, skipping invalid
handles instead of stopping at the first one. Keep it explicit that this
API inspects the initial handles, not all the dynamic handles created
later with other generations.

Recommended regression: deliver at least two extra handles, close the first
and check that the second still appears. Also cover a gap in the middle.
