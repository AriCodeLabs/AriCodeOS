Scope: the `HEAD^..HEAD` diff of that merge and its interactions with the PMM/VMM.
The working tree was clean at the start. No production code was fixed.

following failures. The reproductions were made on a copy of the versioned files

## 1. [P1] A large request overflows the addresses and writes outside the heap

Code: `libs/heap/src/lib.rs:140–142`.

`Heap::allocate` computes the alignment and `user + size` without checking for overflow.
In the kernel region, which starts at `0xffffc00000000000`, a valid 64 TiB `Layout`
overflows `used_end`. In release, the wrapped value wrongly passes the
`used_end <= block_end` check; `insert_free` tries to write the tail to an address
outside the heap. The `HEAP_MAX` limit does not protect this path because
`KernelHeap::alloc` first tries the allocator and only afterwards decides whether to grow.

Reproduction: right after initializing the heap, run
`Vec::<u8>::new().try_reserve(1 << 46)`. It should return `Err`. QEMU exits with
code 35, `ARICODEOS KERNEL PANIC`, a write #PF exception and `CR2 = 0x10`.
The original self-test only uses `1 << 40`, which does not reach this overflow.

Proposed fix: use checked arithmetic to round/align and add addresses, returning
`None` if the result is not representable, before modifying the list. Add a QEMU
regression for the 64 TiB request and another for an alignment that overflows the
rounding in the upper half.

Local evidence: `build/audit/heap-9d8c7e5/overflow/serial.log` and its ESP with the
reproduction kernel.

## 2. [P1] A failed partial growth leaks frames and blocks future growth

Code: `kernel/src/memory/heap.rs:61–68`.

If `p.allocate()` or `map_4k` fails, `grow` returns without undoing the pages already
mapped or returning their frames. It also does not update `mapped` or add that space
to the allocator. The next growth starts again at the same address and fails with
`AlreadyMapped`, even when physical memory is available again.
In addition, the frame acquired right before a `map_4k` failure is leaked.

Reproduction: reserve frames through the PMM until eight are left free, request
8 MiB from the heap, release the frames held by the test and repeat the request.
The output was:

```text
AUDIT: before failure mapped=1048576 free_frames=8
AUDIT: first null=true mapped=1048576 free_frames=0
AUDIT: retry null=true mapped=1048576 free_frames_before=128918 after=128917
```

The second request fails with more than 500 MiB of free physical memory and leaks
another frame. QEMU exits with code 33 because the test records the failure and
continues; that code does not mean the allocator has recovered its ability to grow.

Proposed fix: make the failure leave a consistent state. Unmap and return the
acquired frames (invalidating the TLB where needed), or explicitly add the completed
pages to the heap and advance `mapped`. Always return the frame whose insertion
failed and account for the intermediate tables the mapper may have created. Add a
regression for real PMM exhaustion followed by recovery and a successful retry.

Local evidence: `build/audit/heap-9d8c7e5/oom/serial.log` and its ESP with the
reproduction kernel.

## 3. [P1] The growth path reuses an invalidated mutable reference

Code: `kernel/src/memory/heap.rs:77–86`, in relation to line 68.

`alloc` keeps `heap: &mut Heap` while calling `grow`. That function obtains mutable
access to the same global object again in order to call `add_region`.
Afterwards, `alloc` reuses the earlier reference in `heap.allocate(layout)`.
These are accesses through independent mutable references to the same object,
incompatible with the exclusivity Rust requires; a single CPU and disabled
interrupts do not solve the aliasing problem. The `SingleCpu` contract itself
warns against this pattern.

Proposed fix: limit the first reference to the first allocation attempt and obtain
a new reference after `grow`, or pass the same reference to `grow` so that it uses
a derived borrow and does not access the global again.

Finding by code inspection. No observed QEMU failure is attributed to this problem;
Miri is not available for the installed toolchain `1.98.1`.

## Resolution status

All three findings are pending a fix and their regressions.
The report is kept on the `fix/audit-heap-9d8c7e5` branch, without commit or merge.
The generated evidence lives in `build/`, which is ignored by Git.

# Resolution (branch `fix/audit-heap-9d8c7e5`)

| # | Finding | Fix | Regression |
|---|---------|-----|------------|
| 1 | Address overflow | `Heap::round` uses `checked_next_multiple_of`; the `allocate_rounded` core computes `user` and `used_end` with checked arithmetic and filters `used_end <= block_end` before touching the list. The heap returns `None` and `try_reserve` fails cleanly. | host: `unrepresentable_requests_return_none_and_leave_list_intact` (extreme values on `allocate_rounded`, which cannot be reached on the host with valid `Layout`s); QEMU: `memory.heap_selftest` now requests `1 << 46` bytes and `1 << 34` elements of 4 KiB |
| 2 | Failed partial growth | `grow` is transactional: `map_pages` counts what was mapped and, on failure, `unmap_pages` unmaps, invalidates the TLB and returns the frames; the frame whose insertion fails is released immediately; `mapped` does not advance. Intermediate tables created by the VMM are kept for reuse (documented). | QEMU: `memory.heap_oom_recovers` (`test=heap_oom`): drains the PMM down to 8 frames, requires failure without `mapped` advancing and with at most 4 frames consumed by tables, returns the memory and requires the 8 MiB retry to succeed |
| 3 | Invalidated mutable reference | `alloc` takes a new, short-lived reference to the heap on each attempt; `grow` is the only path that re-enters the global and no `&mut Heap` is alive when it is called. The `SAFETY` comment of `impl GlobalAlloc` documents the rule. | Finding by inspection; no Miri in the toolchain. The structure makes the overlap impossible by construction. |
